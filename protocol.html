Serial output and replay

Embedded Systems. Serial output for the core (C12) and serial replay for the challenges.

Use live serial output when testing the monitor on the board. The serial replay format for advanced challenges will be published before you start them.

  1. Live serial output (C12)
  2. What the Part 1 binary prints
  3. Serial replay for the challenges

1. Live serial output (C12)

Your firmware prints what the monitor is measuring and deciding on the USB serial port, while it runs. Nothing has to be sent to the board to get this output. You use it to test your own firmware, and the lecturer uses it to watch your binary during a check.

The output must show:

  • the live temperature, relative humidity, acceleration (x, y, z) with units. Include angular rate (x, y, z) in Part 2;
  • the health of each sensor separately;
  • the current alarm causes and faults;
  • your build ID, printed once at start-up.

You choose the layout. A person must be able to read it in a serial monitor, and it should update regularly so you can observe the device during a test. State your layout and update rate in your requirements for C12. This Part 2 line is an example:

t=12.40s T=22.6C RH=41.2% acc=(0.02,-0.01,1.00)g gyro=(0.4,-0.2,0.1)dps AHT20=OK ICM=OK alarms=none faults=none

Keep debug text to a minimum on this port, or mark it clearly, so that the live output is easy to read during tests.

2. What the Part 1 binary prints

Part 1 reports live temperature, humidity and three-axis acceleration with units, sensor health, faults and distinct alarms. Mark unavailable readings invalid. Include the current acceleration alarm in the status output. It is active when valid total acceleration magnitude is above 1.5 g and clears on a valid measurement at or below 1.5 g. State your output update rate and show activation and clearing in your physical test. Angular rate is added in Part 2.

3. Serial replay for the challenges

Every challenge (X1 to X6) needs a small serial replay interface. The core and the standard features do not.

Replay sends recorded IMU samples to your board over USB, so that your challenge code can be tested on the same input every time. Signal processing, sensor fusion and machine learning cannot be measured fairly from hand movements alone, because no two movements are the same.

The interface does four things:

  1. Start replay, and reset the processing state of your challenge.
  2. Accept timestamped IMU samples: acceleration x, y, z in g and angular rate x, y, z in degrees per second.
  3. Report the results of your challenge, such as the frequency for X3 or the class for X6.
  4. End replay and go back to the live sensors.
Two rules. Replayed samples must go through exactly the same processing code as samples from the real IMU, so that a replay test tests your real firmware. Your code must take time from the sample timestamps, not from when each line arrives over serial, because USB timing is not steady.

You build the replay receiver in your firmware. The lecturer will supply the message format, a small PC program to send the samples, and example data sets. The format will be published before you start the challenges, after the first submission. If you choose two challenges, one replay interface serves both. Replay does not replace the physical tests: each challenge also needs measurements on the real board.

4. Operating values

These values may change after they are checked on the lab hardware.

ValueSettingWhy
Accelerometer rangeChoose a range that covers the measurements you needAllow headroom for the largest acceleration you intend to measure, particularly for shock recording.
IMU sample rateAt least 50 Hz, with the screen runningKnocks are short, and a slower rate misses them.
Upright reference+Z: breakout flat, components facing up, reading about (0, 0, +1) gTilt is measured from this direction. Check the printed axes and signs on your board.
Smallest usable acceleration for tilt0.5 gBelow this the direction of gravity is not known.

The ICM-20948 breakout hangs on its cable. Treat it as mounted flat with its components facing up, and tilt the breakout itself for physical tests. Its I2C address is 0x69 and the AHT20's is 0x38; do not change either board.
