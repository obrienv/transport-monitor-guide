1. Why there is a test interface

Most of your features can only be tested properly with exact inputs. A test of the 28 °C limit needs a temperature of exactly 28 °C and then 28.5 °C, and a test of stale data needs the sensor to stop updating for a known time. You cannot produce these reliably with a real sensor, so your firmware accepts readings and time from a computer over the USB serial port.

The lecturer's test program uses this interface to test your binary. You should use the same interface to test your own firmware, because a test that you can repeat over serial is a test the lecturer can repeat too.

The one rule that matters most. Readings that arrive over serial must go through exactly the same monitoring code as readings from the real sensors: the same filtering, the same limit checks, the same alarm and fault logic. The serial readings replace the raw sensor readings at the point where they enter your monitoring code. If you write a separate path for test readings, your tests pass while the real monitor stays untested, and the lecturer's hand checks with real heat, cold and tilt will show the difference.

2. The serial link

  • Every message is one JSON object on one line, ending with a newline (LF). Accept CR LF too, by removing the CR.
  • The computer sends one request and waits for your reply before it sends the next one. Your firmware sends exactly one reply line for every request line, including a line it cannot understand.
  • Reply within 500 ms of receiving the newline.
  • Accept lines of up to 1024 bytes. A longer line gets one line_too_long error, and your firmware throws away the rest of that line.
  • Do not print debug text on this serial port, because the test program reads every line as JSON.
  • When your firmware starts and the serial port is ready, it sends one ready message. This is the only message it sends without being asked:
{"type":"ready","protocol_version":"TMTEST-0.7","build_id":"your-build-name"}

Use build_id to identify your binary, for example your student number and a version. It must match the build ID in your documents.

3. Live mode and test mode

Your monitor starts in live mode. It reads the real sensors and uses its own clock. You can still send hello and state.get to watch the live state.

The command test.enter switches to test mode. In test mode the real sensor readings no longer reach the monitoring code. All readings come from samples.update messages, and the time comes from the t_ms field of those messages. Test time starts at 0 ms. The command test.exit goes back to live mode.

Your settings and anything saved in flash memory stay the same when the mode changes. Alarms, timers, filters and the event session start fresh.

Example of hello and its reply:

{"cmd":"hello"}
{"ok":true,"data":{"protocol_version":"TMTEST-0.7","build_id":"your-build-name","supported_commands":["hello","test.enter","case.reset","samples.update","clock.set","state.get","test.exit","ui.action","settings.set"]}}

Add events.get and summary.get to supported_commands only if you implement them.

Every other command except test.exit and the two event commands replies with the full state, in the form {"ok":true,"state":{...}}. The reply to test.exit is {"ok":true,"data":{"input_mode":"live"}}.

5. Sending readings and time

A samples.update message gives the test time and any of the four measurement groups: temperature (°C), humidity (%), accel (g, as x, y, z) and gyro (degrees per second, as x, y, z). Each group has a valid flag and a value:

{"cmd":"samples.update","t_ms":0,"samples":{"temperature":{"valid":true,"value":22},"humidity":{"valid":true,"value":50},"accel":{"valid":true,"value":[0,0,1]},"gyro":{"valid":true,"value":[0,0,0]}}}
  • A group with "valid":false has "value":null. It means the sensor reported a bad reading, so your monitor reports an invalid fault for that group. It is not a protocol error.
  • Each group you send gets the current t_ms as its last-update time. A group you leave out keeps its previous reading and its previous update time.
  • t_ms is a whole number of milliseconds. It can stay the same or go up, but it cannot go down until the next case.reset.
  • clock.set moves the test time on without new readings. A reading is out of date (stale) when the current time minus its last-update time is greater than its maximum age. The maximum ages are 5000 ms for temperature and humidity and 500 ms for the accelerometer and gyro.

In live mode your firmware must still detect stale data using the real times at which it read the sensors.

6. The state reply

{"t_ms":100,"mode":"ALARM","valid":{"temperature":true,"humidity":true,"accel":true,"gyro":true},"readings":{"temperature_c":29,"humidity_pct":50,"accel_g":[0,0,1],"gyro_dps":[0,0,0],"accel_magnitude_g":1,"tilt_deg":0},"faults":[],"causes":["TEMP_HIGH"],"settings":{"temperature_min_c":10,"temperature_max_c":28,"humidity_max_pct":70,"accel_max_g":2.5,"tilt_max_deg":30}}
FieldContents
t_msThe current test time. In live mode, your firmware's own time in milliseconds.
modeFAULT if any fault exists, otherwise ALARM if any alarm cause exists, otherwise NORMAL.
validFor each of the four groups, true if its latest reading is valid and not stale.
readingsThe current usable value of each measurement: temperature_c (°C), humidity_pct (%), accel_g and gyro_dps (x, y, z), accel_magnitude_g (g, gravity included) and tilt_deg (degrees from upright). A value is null when its group is missing, invalid or stale, and tilt_deg is also null when the tilt is undetermined.
faultsA list of {"group":...,"reason":...} objects. The group is temperature, humidity, accel, gyro or tilt.
causesA list of the active alarm causes: TEMP_LOW, TEMP_HIGH, HUMID_HIGH, ACCEL_HIGH and TILT.
settingsThe current value of the five core settings, plus every extension setting you implement (section 7).

In live mode readings shows the real sensor values, so state.get is the way to check that your sensors work. In test mode it shows the values you injected, together with the magnitude and tilt your firmware worked out from them. The lecturer checks your tilt calculation through tilt_deg.

Each measurement group has at most one fault reason. The reason is missing if the group has never had a reading, invalid if its latest reading is invalid, and stale if its latest valid reading is too old.

Tilt has its own fault. When the accelerometer reading is valid but its magnitude is below 0.5 g, the direction of gravity cannot be worked out, so your monitor reports {"group":"tilt","reason":"undetermined"}. At exactly 0.5 g the tilt can still be worked out. If the accelerometer group already has a fault, do not add a tilt fault as well, because the accelerometer fault already explains it.

A fault in one group does not remove the alarms from other groups. A gyro fault, for example, leaves a valid TILT alarm in causes, although mode becomes FAULT. An alarm whose own reading is invalid or stale is no longer known, so it leaves causes. The test program compares faults and causes as sets, so their order does not matter.

Features that need more state fields, such as an armed flag for P05, add them to the state. Describe each extra field, with its type and unit, in your requirements.

A settings.set request and its reply look like this:

{"cmd":"settings.set","key":"temperature_max_c","value":27.5}
{"ok":true,"state":{"t_ms":0,"mode":"FAULT", ... ,"settings":{"temperature_min_c":10,"temperature_max_c":27.5,"humidity_max_pct":70,"accel_max_g":2.5,"tilt_max_deg":30}}}
  • The menu and settings.set must use the same validation code. Both accept only values on the step grid, so 27.5 is accepted and 27.3 is rejected.
  • A rejected value gets a bad_value error (or bad_type for a value of the wrong type) and leaves the old setting in place.
  • An accepted value takes effect at once. In test mode your monitor re-checks the current readings at the current test time.
  • Decide whether a setting changed over serial is saved to flash. If you claim P04 (persistent configuration), say in your requirements when settings are saved.

Challenge commands and state fields, including those for X1 sampling, will be announced.

Event list and summary

events.get replies with {"ok":true,"data":{"events":[...],"csv":"..."}}. Each event has at least id, kind, t_ms, value and unit. List your event kinds in your requirements. For the combined L01 + L03 feature, csv holds the CSV export as one string.

summary.get replies with {"ok":true,"data":{"sample_count":0,"peak_accel_g":null,"max_tilt_deg":null,"temperature_min_c":null,"temperature_max_c":null,"humidity_min_pct":null,"humidity_max_pct":null,"event_count":0}}. A value that is not known yet is null, not zero.

8. Errors

An error reply has the form {"ok":false,"error":{"code":"...","message":"..."}}. The test program checks the code; the message is for people. A rejected request changes nothing: not the readings, not the time and not the settings.

CodeWhen to use it
invalid_jsonThe line is not a valid JSON object.
bad_requestA required field is missing, or the message has the wrong structure.
bad_typeA value has the wrong JSON type, or a vector does not have three numbers.
bad_valueA value has the right type but is outside its allowed range or off the step grid, such as a negative t_ms.
line_too_longThe line is longer than 1024 bytes.
wrong_modeA test-mode command arrived in live mode.
backwards_timet_ms is lower than the current test time.
unknown_commandcmd is not one of the commands in section 4.
unsupportedThe command, action or setting belongs to a feature you have not implemented.
internal_errorYour firmware could not finish the request.

Check a request in this order: JSON, then fields and types, then mode, then time, then run the command. The first check that fails decides the error code.

9. Comparison rules

DecisionRuleAt exactly the limit
Low-temperature alarmtemperature < temperature_min_cNo alarm
Other alarmsreading > limitNo alarm
Stale readingage > maximum ageStill fresh
Tilt alarm clears (P08)angle <= tilt_clear_degClears
Alarm delay complete (P09)time in condition >= alarm_delay_msAlarm starts

Tilt is the angle between the measured gravity direction and the upright reference (section 11). Calculate it to within 0.1°. Rounding makes an angle of exactly 30° impossible to test fairly, so the lecturer's tests never use an angle within 1° of a tilt limit. Temperature, humidity and acceleration limits are tested at exactly the limit.

10. Worked sequence

Use this sequence to check your firmware. It starts with test.enter, then {"cmd":"ui.action","action":"restore_defaults"}, then case.reset. The six steps below follow on from each other.

StepRequestExpected result
1All four groups valid at t_ms 0: 22 °C, 50%, accel (0, 0, 1), gyro (0, 0, 0)NORMAL, no faults, no causes
2Temperature 29 °C at t_ms 100ALARM, cause TEMP_HIGH
3Temperature invalid at t_ms 200FAULT, temperature invalid, no causes, because the temperature is no longer known
4clock.set to 501FAULT: temperature invalid, accel and gyro stale (501 ms old, maximum 500 ms). Humidity is 501 ms old and still fresh.
5All four groups at t_ms 502, with accel (0, 0, 0)FAULT, tilt undetermined. All four groups are valid.
6All four groups at t_ms 503, with accel (0, 0, 1)NORMAL
